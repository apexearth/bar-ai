## Energy generator/converter site safety — dispatched builders to unsafe spots, never landed a converter

apexearth, watching live: "we're overflowing energy and haven't made any
converters." Checked the exact match: `convert-task-added`/
`convert-task-removed hadNanoframe=0` cycled repeatedly at several DIFFERENT
positions in a row (1512,1224 -> 1288,1256 -> 1480,856 -> 370,578...),
interleaved with `con-veto abandon armck -> convert threat=5` -- not a
capability mismatch (already fixed earlier tonight; these were the
T1-buildable small converter, `armmakr`, which armck legitimately can build),
but the site itself reading unsafe immediately after dispatch every time.

**Root cause**: `ReactorSpot` (used for fusion/reactors) already
threat-checks a candidate site before committing (`ThreatFor(unit, site) >
CON_THREAT_VETO`, `rules_optional.as`) -- but the general placement path used
by converters/solar/wind (`Base::Spot`/`CoveredSpot`/pack/home-fallback in
`HomeEnergy`, `mexguard.as`) never did. It relied entirely on the REACTIVE
`AbandonUnsafeSite` check to catch a bad placement after a builder was
already sent there -- so a hot base kept generating fresh bad proposals,
dispatching, aborting, and trying again, without a working fallback,
matching exactly "overflowing energy, zero converters."

**Fix**: `mexguard.as`, `HomeEnergy` -- after the placement ladder picks
`spot` (for any non-reactor generator, which is already screened), check
`ThreatFor(unit, spot) > CON_THREAT_VETO` before dispatching; if unsafe,
retry once at the safe home-fallback search, and if that's ALSO unsafe,
decline outright rather than sending a builder to die on arrival. Matches
the existing pattern `ReactorSpot` already uses for reactors.

**Not yet live-confirmed** -- deploy pending (a watch game was active).

## Commander noTask watchdog — the retreat-dedup fix reduced churn but didn't close the real gap

apexearth, after the retreat-dedup fix: "I still see that commander fire
state toggling. Just less... but there's still lots of time when he stands
around doing nothing. Don't we have good logs on this now?" There was --
`rules_commander.as`/`events.as` already had a per-AiUpdate sampler
(`CommIdleAttribute`) bucketing the commander's task state every tick,
previously used only for a different watchdog (BUILDER task stuck with no
engine order). Its own `noTask` bucket comment already said "the pipeline
declined; that is our bug," never acted on.

Checked the live match: `comm-why samples=931 noTask=516` — 55% of samples
over a ten-minute stretch with the commander under continuous heavy influence
(1.4-99, never near zero, confirmed via the `commander leaving` log) showed
`u.task` literally null/IDLE/NIL, not held-and-stuck. Root cause:

threat. The retreat-dedup fix (above) correctly stopped RE-CREATING tasks on
every re-election, but a re-election isn't happening often enough in the
first place while genuinely idle.

(`cpp/src/circuit/script/BuilderScript.cpp` -- the method already existed,
just wasn't exposed to script) lets the sampler force-assign a fresh
`Retreat()` task directly instead of waiting for the engine's idle callback.
`events.as`'s `CommIdleAttribute()`: after 3 consecutive noTask samples while
influence is still above the flee threshold, calls `Retreat(u)` and
`aiBuilderMgr.AssignTask(u, fresh)` directly, logging `apex: commander forced
back onto retreat`. `comm-why`'s log line now also reports the `forced`
counter for visibility.

Built clean via docker toolchain. **Not yet live-confirmed** -- watch for the
`forced` counter staying near zero in a normal game (it should only fire
during genuinely sustained danger) and `noTask` share dropping sharply in the
next watched match's `comm-why` line.

## T2 lab placement — a SECOND, distinct gap from the earlier rear-placement fix

apexearth: "When we make our T2, we have built it towards where the enemy
is... losing it usually means game over during T2 transition time." Earlier
tonight's fix (`GetTaskCountOf` -> `GetDefBuildProgress` gate) was confirmed
NOT the cause here -- checked the live match directly: `armalab` (the actual

def that actually needed it.

**Fix**: `factorydefs.as`, new `Factory::NextT2Counterpart()` -- checks EVERY

remembered opening one) and returns the T2 counterpart of the first one not
yet started. `AdvancedPlantAtRear` (`rules_optional.as`) switched to it.
`AdvCounterpart()` itself left in place (still used by other callers with a
different, opening-factory-specific question).

## Commander "swapping fire states, standing around doing nothing"

apexearth, watching: "swapping between fire at will and return fire, idk
what else they're thinking about." Checked the exact match's own log first:
`apex: commander leaving, enemy influence` fired every ~15s (the log's own
throttle) for the ENTIRE 11-minute match, influence ranging 1.4-38 --
continuously above the flee threshold, never flickering near it. So the
decision itself (flee now) was correct and stable every time; the commander
just never got to finish leaving.

**Mechanism**: `CBuilderManager::EnqueueRetreat()` (engine C++,
`BuilderManager.cpp`) always `new CRetreatTask(this)` -- no dedup against an
existing retreat, unlike every other task path in this codebase (which joins
an in-flight request by site). Every flee/abandon branch in
`rules_commander.as` (5 sites), `rules_hold.as` (2), and `rules_rezzer.as` (1)
called it fresh on every re-election, on an explicitly-documented but wrong
assumption ("re-enqueuing an existing retreat is a cheap no-op"). A fresh
`CRetreatTask` object means a fresh `AssignTo`/`RemoveAssignee` pair on the
SAME unit each time: `AssignTo` tears down and rebuilds the travel action and
sets fire state to RETURN (cloak-capable units only, which includes the
commander); the previous task's `RemoveAssignee` restores the def's default
OPEN fire state. Net effect, once per re-election (~1s) for as long as the
flee condition holds: fire state flickers RETURN/OPEN, and the travel order
never survives long enough to make progress -- exactly "standing around
doing nothing" while continuously "fleeing."

**Fix**: `Builder::Retreat(unit)` (`sitesafety.as`) -- returns the unit's
already-held task if it's already `Task::Type::RETREAT`, only calling
`EnqueueRetreat()` for a genuinely new flee. All 8 call sites across the
three files switched to it. Same "check what's already held before asking
for new work" pattern as every other re-election-thrash fix this session.

**Deployed together with the geo income gate above.** Both AngelScript, no
build step. Not yet live-confirmed -- watch for `apex: commander leaving`
firing once per genuine flee episode rather than every ~1s, and the commander
actually covering ground when fleeing continuous influence.

## Geothermal energy — new capability, not a bug fix

apexearth: Geyser Plains has lots of geo vents and geo is "fantastic
efficiency... energy eco just like any other energy eco." Investigated why
apex never built one: `HomeEnergy` (`builder/mexguard.as`), the ranked
energy-per-metal ladder that already covers wind/solar/adv-solar/fusion,
never had geo in it at all, and no AngelScript binding existed to find a geo
vent in the first place (`InitScript.cpp`/`EconomyScript.cpp` grepped, zero
hits) — geo was only reachable through the native engine's own
`UpdateGeoTasks`, called purely as a last resort when every other energy def
is exhausted, and even that native path excludes ally-zone (home) vents by
design (mirrors `FindOpenMexSpot`'s own frontier-only exclusion).

Added the missing binding trio (`FindOpenGeoSpot`/`GetGeoSpotPos`/
`EnqueueGeoAt` on `CEconomyManager`, `cpp/src/circuit/module/EconomyManager.
{h,cpp}` + `cpp/src/circuit/script/EconomyScript.cpp`), deliberately WITHOUT
the ally-zone exclusion since a home vent is exactly what should get built.
`GetEnergyMake` already prices a geo def correctly (reads its map-specific
`SGeoExt::make` value), so once a vent could be found, `EnergyValuePerMetal`
slotted geo straight into the existing ranking with no new value logic.
Wired into `HomeEnergy`: geo only enters the ranking once an open vent is
actually found (otherwise it would win unconditionally and jam the ladder on
a vent that doesn't exist, the same trap already documented for fusion);
winning geo takes its own placement path (`EnqueueGeoAt` with the vent's
spotId) instead of the generic layout-grid/Base::Spot flow every other rung
uses, since a geo plant must sit on a fixed tile. Excluded the commander from
the geo candidate (armgeo's own buildoptions start at armcomlvl3, same
blanket exclusion `IsAdvConDef` already applies to the advanced-tower tier).

**Smoke-tested and confirmed working, not just compiled**: 10-minute headless
match on Geyser Plains (has real geo vents). `apex: home energy armgeo geo
spot=4 ...` fired at minute 2.2; `[BARAI_POS]` snapshots show a real standing
`armgeo` unit from minute 6.0 through 9.2; it was then lost to a combat raid
(`unit-destroyed armgeo ... curTask=t0b-1`), a normal battlefield death, not
a construction failure. First smoke test also caught the commander trying
`armcom -> armgeo` and being correctly blocked by tonight's `CanBuild` guard
(level-1 commander can't build it) — fixed by excluding the commander from
the geo candidate up front, redeployed, not yet re-tested after that specific
change (low risk, same shape as the already-verified `IsAdvConDef` pattern).

## Idle/passing builders and unclaimed mexes — three separate gaps, same symptom

1. **Idle next to a mex, walks off**: `FindOpenMexSpot` excludes ally-zone
   (home) spots, so `Brain::Decide` never proposes a home mex and an optional
   want wins instead. Fixed: `Builder::MexOffer` (`rules_offer.as`) takes a
   safe engine-offered mex task immediately, ahead of any optional want.
   Partial — only helps once the engine's own scan has reached that spot.
2. **Passing a mex mid-walk, doesn't detour**: `HoldWorkInProgress`
   (`rules_hold.as`) unconditionally holds any named in-progress task and
   runs before `DefaultMakeTask`/`MexOffer` are even called — so a builder
   walking anywhere else never gets a chance to consider a mex it's passing.
   Fixed: `Builder::PassingMex`, checked ahead of the hold, takes a mex if the
   detour is ≤35% of remaining travel distance; the new mex task is then held
   normally so it can't re-thrash. Only covers frontier mexes (script-visible
   ones); home mexes still depend on `MexOffer`.
3. **Two mexes next to a fresh tower stayed unclaimed for minutes**:
   investigated, not fixed — two candidate mechanisms (own defence gets no
   threat-map credit near a contested tile; or the ally-zone scan-cadence gap
   from #1) need a real match log to distinguish. Logged in `ISSUES.md`.

Also: general-path task stickiness didn't cover RECLAIM tasks
(`SiteBuildName` excludes them), so a builder mid-reclaim could be thrashed
off by a fresh `DefaultMakeTask` offer — fixed by holding RECLAIM the same
way. And no rule proposed reclaiming neutral trees/wrecks when a builder was
genuinely idle — added `Builder::IdleFeatureReclaim`, floor-tier only,
`minMetal=1`.

## Builders join/assist a build that will finish before they arrive

`Requests::JoinFor`/`Redirect` (`requests.as`) ranked candidates on build
progress then distance, with no travel-time check. Added `WorthJoining`:
estimates remaining build time (`cost*(1-progress)/(DRAIN*busyWorkers)`)
against `distance/ASSUMED_CON_SPEED` (40 elmos/s, grounded in real T1 con
speeds — no per-unit speed binding exists to do this exactly). Skips the join
if the walk outlasts the remaining build. Approximation, not exact ETA;
`ClaimFor` (zero-worker sites) and same-site `CoverFor` joins left untouched.

## General CanBuild guard — closes the whole "assigned an unbuildable def" class

`CCircuitDef::CanBuild()` (a real buildoptions lookup) existed in C++ and was
never exposed to script. Bound it (`InitScript.cpp`) and wired
`Builder::GuardBuildCapability` as a single guard at the end of `AiMakeTask`
that blocks any task naming a def the assigned unit's buildOptions don't
contain — pipeline-wide, and correct for modded units since it reads real
engine data rather than name/cost heuristics. `IsAdvConDef` (the earlier,
narrower cost-heuristic fix for the same class, see below) left in place
alongside it as a more specific check.

## AA: two separate bugs — overbuild with no threat, and misuse in ground attacks

**Detection latency**: `AirCoverWant`'s presence gate used a 240s-smoothed
average, so a real raid took up to 4 minutes to register — measured zero AA
built across a 19-minute game despite the enemy's raw air cost reaching 4924.
Fixed: gate on `AirThreatNow()` (raw current tick), size on

`RT::AA`, reverting to stock `CAntiAirTask` routing.

  toward the already-tuned tier3 endpoint for `armfido`/`armfboy`/`armsnipe`
  (Armada), `cormort`/`corsumo` (Cortex), and `leginc` (Legion's actual T2
  assault/heavy twin — corrects an earlier wrong claim that Legion has none;
  that was about `legkeres`, a different T3 unit). `leginc` was hard-zeroed
  worse than Hound ever was (0.00 through tier2, cliff to 0.40 at tier3).
- Support/utility units (radar/jammer/spec-ops: `corvoyr`/`corspec`/
  `armmark`/`armjam`/`corvrad`/`cormabm`, Legion's `legaradk`/`legajamk`) had
  the same hard-zero shape at tier0/1, all lumped into one low-`importance`
  "support" role. Unfroze to 0.03, same precedent as Sniper. Full role-
  taxonomy split (separate radar/jammer/spec_ops roles) not attempted —
  flagged as its own follow-up in `ISSUES.md`.
- `response.json` itself confirmed correctly weighted across three

## Rez bots: repair/support gaps

- **Idle next to a damaged mobile unit, did nothing**: `CBuilderManager` had
  no native `damagedHandler` for ordinary mobile units (only for
  builders-taking-damage and static structures). Added `CCircuitAI::
  GetOwnDamagedNear` C++ binding + `Builder::RezzerRepairNearby`, floor-tier.
- **Repair throttled team-wide**: `RezzerRepairNearby`'s gate was a single
  global clock shared by every rez bot (copied from a pattern correct for an
  expensive team-wide *scan*, wrong for a per-bot *assignment*) — capped the
  whole team to one new repair per second regardless of how many bots were
  idle. Fixed to gate per-bot via existing `ConSlot` tracking.
- **Never follows the army, only retreats toward it**: only rule that reaches
  beyond a rez bot's own position was gated on `Military::LosingGround()` —
  entirely home-bound while winning, which is when corpses/damage pile up at
  the advancing front. Measured: `mRezSpend` ~5% of what was spent building
  the bots. Fixed: also fires when the bot's own local wreck search is empty.
- **Damaged static structure (HLT) ignored by both commander and rez bot**:
  the native repair task for a damaged structure DOES exist and fire
  natively, but two independent native gates blocked anyone from getting it —
  the engine's own task-ranking skips any non-critical task sitting on
  contested ground (a bare boolean, not graded), and `CBRepairTask::
  CanAssignTo` unconditionally excludes commanders from any repair task.
  Fixed: `Builder::RepairStructureNearby` claims the target directly via
  script (bypasses both native gates, same technique as the mobile-repair
  fix), wired for both non-commander builders and the commander.
- **Native "heal everything in this radius" order exists in the engine**
  (`CMD_REPAIR` with a radius param) but nothing in this codebase issues it —
  every repair here goes through the `IBuilderTask` one-target model. Wiring
  the native order in for rez bots specifically would bypass this AI's whole
  task-tracking system for one unit class; not attempted, real limitation.

  second T1 lab silently vetoed the rule, falling through to stock placement
  with no home bias. Fixed with a per-def check.
- **T2 committed with an economy gate but no safety gate**: `RushReady()`
  read only metal/energy income; a 1v1's own economy was genuinely healthy
  when T2 committed, but nothing checked whether the base was safe to commit
  *from* (factory line idles, army-value switch check waived by design).
  Added `!Military::LosingGround() && !Military::BaseContested()` — reuses
  signals `defenceline.as` already trusts for the same question. Not a
  team-size branch (an earlier, different attempt at that was measured under
  the since-removed solo-stock gate and isn't valid evidence either way).
- **"Excess con power into defence when under attack"**: investigated, no
  gap found. `DefenceAllowedAt`'s `pressureAllow` term already doubles the
  front budget under contest, and was firing correctly in the match checked —
  defence spend grew right up to the final ~60-90s, when the whole base
  (factories, mexes, everything) died simultaneously to total overrun, not a
  defence-valuation stall. One real, unmeasured refinement logged in
  `ISSUES.md`: the escalation is a flat 2x boolean, not graduated by how
  badly the fight is going, and `BaseContested()` only trips once the enemy
  already holds ground (a late trigger).

## Factory queue: T1-only lines could spend 100% of their queue on constructors

`brain/facqueue.as`'s constructor floor is checked first and the fill loop
breaks on the first short floor — combat defs are only reached once every
floor is met. `T2ArmyShort` already reorders this in the army's favor once a
line has T2 buildoptions; no equivalent existed for a still-T1-only line.
Measured: one match's T1-only factory spent `armck:2200` vs all mobile combat
`749` metal combined over 11 minutes. Added `T1CoreWanted()`/`T1ArmyShort()`,
same income-scaled shape, gated on the complement of `T2ArmyShort`'s own
condition. Deployed and smoke-tested (3 headless matches): confirmed via a
temporary debug log that it fires once and releases once the floor is met,
then confirmed a clean final build holds `armck` flat while combat units
keep growing on a still-T1-only line. Not confirmed at matching scale/ratio
against the original bug report (only an 8-minute smoke test).

## Squad combat: standoff, retreat, and tower-diving (Layer 3, C++)

Several rounds on the same underlying complaint ("units run too deep / dive
into towers"), landed across the evening:

- **Coward-rear screening**: units at/below `GetRetreat()` health, when still
  safe to keep fighting, now stand 35% further out on the same ring
  (`COWARD_REAR_MOD`) instead of the squad dissolving one unit at a time into
  full retreat. Measured 1v1 self-play: disadvantaged side's K/D moved
  0.306→0.643 (before never broke 0.43 in 6 games; after broke 0.9 twice).
- **In-range threat veto had no distance check**: a unit not yet in weapon
  range could get stuck holding position indefinitely because every
  candidate step toward the target read "hotter" than staying put. Gated the
  veto on already being within standoff range. Measured: disadvantaged
  side's K/D 0.752→0.968, enemy static kills roughly doubled both sides.
- **Standoff 95%→90% of own range** (matching apexearth's explicit number),
  **LOS-standoff scout had no floor** (could send a unit to `min(range,
  sight)` instead of the real standoff — Hound's 400 sight vs 650 range put
  it at 55% of its own range, deep in enemy return-fire), **ring-side
  selection now weighs threat** (previously pure geometry). Measured
  (symmetric change, judged on total losses not win ratio): combined losses
  -20%, static kills +19%, economy unaffected.
- **Tower-diving, three passes**: (1) a unit correctly holding standoff but
  out of LOS would get a walk-to-target order the next time it was reissued
  — fixed by skipping the LOS requirement for static targets. (2) an
  "outranging" row's standoff had no floor against the target's own range, so
  a target within 90-100% of the row's range still got reached — floored at
  `target_range * 1.1`. (3) apexearth reported the symptom persisted after
  (1)+(2) deployed; full order-path audit found no bypass in the squad task
  itself — found and fixed the same missing-floor gap in the separate
  solo/scout fighter path instead (doesn't explain the reported case, which
  is squad-routed; flagged as such rather than claimed as the fix).
- **Fragile-unit caution scaling**: low-HP units used the same flat standoff/
  safety-threshold constants as tanky ones. Added per-row `fragility =
  avgSquadHealth/rowDef.GetHealth()` (clamped, squad-relative not global),
  scaling both standoff distance and ring-safety sensitivity — generalizes to
  any low-HP def, not a Hound special case.

## Crash fixes (Layer 3, C++)

The long-recurring "IRefCounter::Release() -> delete this" crash, surfacing
at different call sites each time: `ITaskModule::DequeueTask` fired the
script `AiTaskRemoved` callback with no reference held across the call, so
AngelScript could legitimately free the object mid-function, leaving the
native code's own pointer dangling one line later. Same bug class found and
fixed at three sites (`DequeueTask`, `CIdleTask::Update`'s two `Start()`
call chains) — found via Windows Application Verifier plus `addr2line`
against the unstripped build. Fix: bracket each callback with `AddRef()`/
`Release()`. Stayed UNVERIFIED in `ISSUES.md` until a long watched game goes
without a recurrence — three separate crashes were needed to find three real
sites; a clean rebuild alone was not sufficient evidence twice already.

A Linux+ASan harness was built to catch a second, still-unresolved crash
(`MakeBuilderTask`/`buildTasks` dangling pointer) but hit unrelated
init-order crashes specific to the hand-assembled Linux build before
reaching it; dropped as not worth the cost, Windows addr2line remains the
proven pipeline.
