# Changes — 2026-08-14

## 2026-08-14: opening-sequence income gate made economy-only, no time cap

Layer 2 (AngelScript), `builder/opening.as`, `factory/choose.as`. The step-2
"income before the first lab" gate (`OpeningNeedsEconomy`, see opening.as) had
a safety-valve deadline, `OpeningGateMax()`/`apex_opening_gate_max` (180s),
that force-released the gate on elapsed frame count regardless of economy.
apexearth, before this shipped: code it open-ended — a team wiped to one
constructor must re-derive the SAME opening from its current mex/income/
factory readings, not be told "you're 40 minutes in, skip the gates". A frame
check does exactly the opposite: after a wipe the surviving constructor's
fresh opening would already read as past the old deadline.

Removed `OpeningGateMax`/`apex_opening_gate_max` entirely rather than
replacing it with another derived cap. No replacement valve was needed: the
only work `OpeningEnergy` ever proposes comes from `HomeEnergy`, which is
already demand-bounded ("bounded by demand, not a clock" — mexguard.as) and
returns null once there is no beneficial generator or converter left to site.
When that happens the gate still reads "income short" but has nothing left to
spend on, so `MakeTaskInner` falls through it to whatever the engine offered
instead — the gate can cost build power, never deadlock a player. The rest of
`OpeningNeedsEconomy` (`Factory::HaveAnyFactory()`, `GetTaskCountOf(FACTORY)`,
income vs. `OpeningEnergyGate`/`OpeningMetalGate`) was already read from
current standing state, not a one-time flag, so it was already reentrant
post-wipe; only the deadline line was time-keyed. Updated the matching comment
in `choose.as` (`AiGetFactoryToBuild`'s STEP 3 gate), which had documented the
old deadline as the reason the gate can't deadlock. Not yet re-measured in a
match; the change is a straight removal of a clause that only ever fired as a
worst-case fallback.

## 2026-08-14: many DIFFERENT sites of the same building opened at once — VERIFIED

Layer 2 (AngelScript), `builder/joinbuild.as`, `mexguard.as`, `fusion.as`. A
fourth gap in the same duplicate-energy chain, caught by apexearth live on the
build that had already shipped the SAME-TILE fix: "6 advanced solars being
made at the same time... they start making more while others are obviously
already in progress! You're doing a terrible job at fixing that."

**He was right, and it was a real gap, not a repeat of an earlier bug.**
Inspected the live match's `_engine` infolog while the game was running:
`[BARAI_POS]` snapshots showed team t2 with **6** `armadvsol` standing at
once and team t7 with **8**, every one at a genuinely DIFFERENT tile.
`SpotCollides` (the previous fix) never had a reason to refuse any of them —
it only catches a second building on the SAME ground. Nothing bounded how
many DIFFERENT sites of one def could be open together: each site hit its
own `JoinBuilderCap` (income-floored at 2), and the excess builder — instead
of waiting — started a brand new site elsewhere, which then filled its own
cap and handed off again.

Added `BusyOnDef`, counting live builders across EVERY site of a def (not
just one), and made `SiteBlocked` refuse a new site once that TEAM-WIDE total
already meets `JoinBuilderCap` — the same income/drain formula already
verified tonight for a single site, applied as a ceiling across all of them.
This is the same "K items in parallel land at KT/B, nothing pays until then"
argument from the original reactor fix, generalized past reactors: an economy
that can usefully feed `income/drain` lathes on one kind of building cannot
usefully feed more of them spread across five buildings instead of one.

**Verified against the mechanism directly, not by absence of evidence.** The
first reproduction attempt (same map/seed as the prior fix's test) never hit
the condition at all — 0 gate firings, 0 bursts, before AND after — so that
alone proved nothing. Added telemetry to the gate itself
(`apex: site-blocked <def> busy=X cap=Y byCap=N byGround=M`) and ran three more
seeds; one (seed 2, `matches/20260814-003541-*`) triggered it 17 times on
`armafus` (busy reaching 5-7 against a cap of 5-7). In that exact run — the
one that would have produced a burst without the fix — the maximum same-team,
same-def enqueue rate is 1 per 20-second window, and the maximum concurrent
open-sites count in any 100-second span is 3, spread across the window (normal
ladder progression), not clustered (the live game's 6-8 simultaneous). No
compile errors, no crash, across all four seeds.

## 2026-08-14: squad-relative "screen the hurt unit" retreat, measured on a 1v1 mirror

apexearth, watching several games: "our army doesn't fight as unified as the
other army... we give up on successful attacks too quickly." Prior session
diagnosed the mechanism (`military/posture.as:170-178`): outside a declared
`TEAM PUSH`, `ai.SetCommitted(false)` is the normal state, so `CCircuitAI::
IsCommitted` lets each unit peel off individually at its own `GetRetreat()`
threshold -- a squad dissolves one unit at a time. Forcing full commitment
outside a push was tried and reverted (army K/D 0.38 vs stock 1.73). His
refinement: don't force them to fight to the death OR send them all the way
home -- "best would be if the hurt guys just move towards the back of the
pack," screened by healthier squadmates, still in the fight.

**Mechanism.** `IFighterTask::OnUnitDamaged` (`FighterTask.cpp:144-207`)
already has a middle state that was going unused for exactly this: a unit
at/below `GetRetreat()` health is inserted into the `cowards` set (not sent
to `CRetreatTask`) whenever it is still safe -- target in LOS, in range,
threat tolerable (`FighterTask.cpp:191-206`). It keeps fighting at its normal
squad slot and only retreats once it goes idle. The gap was purely
positional: `ISquadTask::Attack`'s per-unit standoff `r` (`SquadTask.cpp:805`,
the radius each unit stands from the target on its row's arc) made no
distinction for a `coward`. Changed `r` to a `float` and multiplied it by
`apex_coward_rear_mod` (default `COWARD_REAR_MOD = 1.35`, `SquadTask.h`) for
any unit in `cowards` -- it stands 35% further out on the SAME ring, which
puts healthier squadmates on the same bearing between it and the target,
instead of leaving the formation. This is not the reverted "never retreat"
change: that forced every unit, healthy or not, to fight in place until
death; this only repositions units `OnUnitDamaged` already judged safe enough
not to need a full retreat. `cpp/src/circuit/task/fighter/SquadTask.cpp:805-
816`, `SquadTask.h` (new `COWARD_REAR_MOD` define). Rebuilt via the docker
toolchain (`ninja -C /build/out BARb`), compiled clean, redeployed
(`deploy_ai.py deploy apex`, confirmed "SkirmishAI.dll (local build)").

**Measured**, self-play (same DLL both sides, isolates the box/map asymmetry
as an identical confound across both runs -- not a code effect), 1v1 Cortex
mirror, Altair_Crossing_V4.1 (a real 1v1 map, 8x8), 15-minute cap,
`--modoption apex_solo_stock=0` (required or a 1v1 silently runs near-stock,
see CLAUDE.md), 6 games each, seeds 1000/1001/1002 x2, `tools/fight1v1.py`:

| | before | after |
|---|---|---|
| team0 army K/D (metal) | 0.306 | 0.643 |
| team1 army K/D (metal) | 2.142 | 1.042 |
| K/D ratio (team0/team1) | 0.143 | 0.617 |
| per-game team0 K/D range | 0.22-0.43 (all 6 below 0.43) | 0.28-1.44 (4/6 above 0.49, 2 above 0.9) |
| metal produced ratio | 0.922 | 0.984 |
| army (real) peak share | 34.3% | 32.8% |
| static defence peak share | 12.4% | 11.1% |
| mex/cons peak (cons T1) | 22 | 22 |

Both runs are self-play, so the map's box asymmetry (team0 consistently the
weaker start on this map -- reused seeds land team0 at the same disadvantage
both times) is present identically in both tournaments; what changed is how
close to parity the fight settled. Before the change team0 never broke 0.43
K/D in 6/6 games; after, it broke 0.9 twice and the aggregate ratio moved
4.3x closer to even. Both sides' K/D moved toward 1.0 together, consistent
with the mechanism: a losing army that used to shed units into full retreat
one at a time (feeding a "smaller army loses faster" spiral) now keeps its
hurt units contributing fire from a safer slot in the same formation.
Economy composition (constructors, army share, metal produced ratio) is
essentially unchanged, so this did not come at a mex/build-power cost.

**VERDICT: measurable improvement, keeping it deployed.** The trade-ratio gap
closed 4.3x on a real, if small (6-game, one map, one faction, one box
layout), sample. Confidence is moderate, not high: only one map/faction/box
config was tested, `COWARD_REAR_MOD` was not tuned (used the first reasonable
guess, 1.35), and 6 games with duplicated seeds is a small sample by this
repo's own noise-floor standard. What would falsify this: the same test on a
different map (different box geometry, where "further out" might route a
coward through a flank rather than behind the line), on Armada/Legion (the
"further from target" positioning is faction-agnostic by construction --
range-row based, not a hand-tuned formation shape -- but not separately
verified), or at a larger N. Left deployed rather than reverted; did not run
a second variant (tuning `COWARD_REAR_MOD` or gating by squad size) this
session given the time already spent on the rebuild/measure loop.

## 2026-08-14: the "hold instead of stepping into a hotter spot" threat-veto had no in-range check, so an approaching unit could get stuck holding position with a target set

apexearth: "sometimes our units will set target on an enemy unit but they
aren't within range. They should be setting target but still have actual
move logic happening which maneuvers them within the range of the enemy."

**Mechanism.** `ISquadTask::Attack` (`SquadTask.cpp:816-844`) computes each
unit's standoff point `newPos` on a ring at its own weapon range from the
target, then (added 2026-08-13 for a different complaint, "retreat logic
takes us into new threats") compares threat at `newPos` against threat at
the unit's current position `curPos`; if `newPos` reads hotter, it replaces
`newPos` with `curPos` -- hold instead of step. That veto had no distance
check at all. `newPos` sits, by construction, at the unit's own weapon range
of the target -- inside or adjacent to the target's own threat radius for
any direct-fire matchup -- so for a unit that has NOT yet reached firing
range, almost every candidate step compares hotter than staying put, and the
veto holds it at `curPos` indefinitely. `CmdSetTarget` still goes out on the
same call (`CCircuitUnit::Attack`, `CircuitUnit.cpp:568-569`), so the unit
visibly has a target locked while never approaching it -- exactly the report.
The comment introducing the veto was explicit that it meant "enemies we're
actively fighting," i.e. a unit already in range choosing not to step into a
second enemy's range; it was never meant to gate the initial approach, but
nothing in the code enforced that scope.

**Fix.** Gated the veto on the unit already being within its own standoff
range of the target (`curPos.SqDistance2D(tPos) <= SQUARE(r * 1.05f)`, `r`
being the same per-unit ring radius already computed a few lines above for
`newPos`). A unit still closing distance is no longer eligible to be held in
place by this check at all -- it always gets the move-toward-range order;
only a unit already trading fire can choose to hold rather than step into a
worse spot. `cpp/src/circuit/task/fighter/SquadTask.cpp:833-850`. Left
`FighterTask.cpp`'s equivalent single-unit `Attack` path (non-squad fighters)
untouched -- it has no such threat-veto block, so it was not part of this
bug. Rebuilt via the docker toolchain (`ninja -C /build/out BARb`), compiled
clean, pulled into `cpp/` via `sync_cpp.py pull`, cumulative patch
regenerated.

**Measured**, self-play (same DLL both sides), 1v1 Cortex mirror,
Altair_Crossing_V4.1, 15-minute cap, `--modoption apex_solo_stock=0`,
6 games each, on an **isolated copy of the engine version directory**
(`recoil_2026.07.04_rangegate_test`, deleted after) so the live install
serving apexearth's own running match was never touched or deployed over --
confirmed via `deploy_ai.py deploy apex` correctly refusing twice while
`spring.exe`/`spring-headless.exe` were open. `tools/fight1v1.py`:

| | before | after |
|---|---|---|
| ARMY K/D (metal), weaker box side | 0.752 | 0.968 |
| ARMY K/D (metal), stronger box side | 1.245 | 0.901 |
| K/D ratio (weaker/stronger) | 0.604 | 1.074 |
| metal produced ratio | 0.867 | 0.952 |
| enemy static killed (weaker / stronger side) | 1570 / 1153 | 2567 / 3888 |

Same map/seeds/box-asymmetry methodology as the coward-change measurement
above, so the two are comparable: the disadvantaged side's K/D ratio moved
from 0.60 to 1.07 -- past parity, not just toward it -- and metal-produced
ratio moved closer to even too, consistent with a squad that no longer

**VERDICT: confirmed bug, fixed, and measured as an improvement.** Not yet

## 2026-08-14: the recurring crash — found and fixed (IRefCounter use-after-free in DequeueTask)

Layer 3 (C++), `module/TaskModule.cpp`. Full writeup in `ISSUES.md`
("RESOLVED" entry) -- summary here for the changelog.

`ITaskModule::DequeueTask` called `task->Stop(done)` immediately after
`TaskRemoved(task, done)`, which fires the AngelScript `AiTaskRemoved`
callback with a bare native pointer and no reference held across the call.
`IUnitTask` is `asOBJ_REF` with intrusive refcounting (`RefCounter.cpp`), so
if that callback happened to drop the last script-side reference (e.g. the
last element removed from `Requests::gLive`), AngelScript legitimately
deleted the object right there, and `task->Stop(done)` one line later was a
use-after-free on the same function's own raw pointer. This is the same bug
class as `changes/2026-08-09.md`'s "C++ deleted tasks the script held," just
the other direction -- script deleting an object native code still needed,
instead of native deleting one script still held.

Found via Windows Application Verifier (`appverif -enable Heaps -for
spring-headless.exe`; no rebuild needed, disabled again after with `-disable
* -for spring-headless.exe`) plus the existing `addr2line`-against-unstripped-
build pipeline from earlier tonight -- AppVerifier didn't catch this
specific bug directly (it's not raw OS heap corruption; AngelScript uses its
own internal pool), but running under it still produced a crash whose stack
pointed straight at the real line. This explains why the crash surfaced at
four different-looking call sites across the session (`CIdleTask::Update`,
`MakeBuilderTask`, `MakeCommDangerTask`, `CBuilderManager::UnitIdle`) and
evaded two sessions of manual auditing -- same root cause, different
downstream victim each time depending on what happened to dereference the
dangling pointer first.

Fix: bracket the callback with the object's own `AddRef()`/`Release()`, the
same guarantee every other handle-holder already gets from AngelScript.
Rebuilt via docker, verified clean AS compile and unregressed opening timing

## 2026-08-14: standoff range tightened to 90%, the LOS-scout mechanism could pull a unit well inside that standoff, and ring-side selection now weighs threat

apexearth, watching live, follow-up to the pre-range threat-veto fix above:
"When we are doing this maneuvering while using 'set target' we should aim
to be at around 90% of our maximum attack range. We should not move any
closer, and we should try to choose safer angles. Right now I see our hound
units running much too deep into enemy territory while fighting enemies
from too close up." Three distinct mechanisms in the same `ISquadTask::
Attack`, `cpp/src/circuit/task/fighter/SquadTask.cpp`.

**1. Standoff was 95% of own range, not 90%.** `STANDOFF_RANGE_MOD`
(`FighterTask.h:19`, runtime `apex_range_mod`) was `0.95f` -- close enough to
the weapon's edge that the enemy's own return fire reaches on a same-range
matchup or the slightest closing move. Changed default to `0.90f`, matching
the number he gave directly.

**2. The actual "running too deep" mechanism: the LOS-standoff scout had no
floor.** `SquadTask.cpp:722-727` (now :722-740) sends the first unit of the
first row to `min(kv.first, rowDef->GetLosRadius()) * rangeMod` instead of
the normal standoff, whenever the target is static or not currently in our
LOS -- so that unit can get a visual lock rather than fight blind. Read
armfido (Hound) from the pinned tree per the 2026-08-09 EyesForTheGuns note:
**650 weapon range, 400 sight.** For a Hound-shaped unit that condition
computes `min(650, 400) * 0.9 = 360` -- 55% of its own range, deep inside
where a 650-range enemy gun reaches it right back. The condition is not
Hound-specific: `isStatic` alone triggers it, so it also fires on every
static-defence target regardless of the attacker's own sight, which is why
the isolated self-play test below (Cortex, no Hound in the roster at all)
still measured a real effect from this line. Floored `range0` at `range`
(`std::max(range, ...)`): a row whose sight already reaches its own standoff
gets the same value as before (no-op, verified: `min(kv.first,losRadius) *
rangeMod` already equals `range` whenever `losRadius >= kv.first`), and a
row that does not is no longer sent closer than the standoff to get there.
The mobile-radar escort added 2026-08-09 (`EyesForTheGuns`) is the intended
fix for genuinely blind guns now; this scout mechanism should not also be
sending the gun itself into danger to solve the same problem twice.

**3. Ring-side selection had no safety preference.** `SquadTask.cpp:768-777`
(now :768-794) computes two candidate ring ends (`newPos1`/`newPos2`,
mirror images of the same standoff arc) and picked whichever was less travel
for the row's lead unit -- pure geometry, no read of what was actually on
either side. Added a threat comparison using the same `CThreatMap::
GetThreatAt` the standoff veto already calls, sampled once per row on the
two candidate ends: the meaningfully-safer side (>10% threat difference)
wins outright, and distance is kept only as the tiebreak when neither side
reads as more dangerous, so the formation does not zigzag between two
near-identical tiles every update.
