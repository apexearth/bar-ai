## 2026-08-14: idle rez bots never repair a damaged unit standing next to them -- FIXED (needs DLL rebuild+deploy, not yet verified)

apexearth, live-watching a 1v1: "We have a lot of rezbots standing around
doing nothing while units next to them need to be repaired." Rez bots are
armrectr/cornecro/legrezbot -- the game's own tooltip calls them "Rez / Repair
/ Reclaim Bot" (`tools/unitdef.py armrectr`/`cornecro`).

**Root cause, confirmed in the C++ core, not the AngelScript pipeline.**
`CBuilderManager::InitHandlers` (`vendor/circuitai/src/circuit/module/
BuilderManager.cpp:264-313`) only registers a `damagedHandler` for two
categories: builders/rez-bots taking damage themselves (their own retreat
logic), and static structures (`buildingDamagedHandler`, priority HIGH). An
ordinary MOBILE combat unit gets no entry in that map at all, so
`CBuilderManager::UnitDamaged` (line 575) is a silent no-op for it -- no
REPAIR task is EVER created for a damaged tank/bot standing in the field,
however long it stands there. `AiMakeTask`'s rez-bot rules
(`manager/builder/rules_rezzer.as`) never saw this because there was nothing
to see: `DefaultMakeTask` had no REPAIR task in its queue to offer, so an
otherwise-idle rez bot fell through to `Assist::Fallback` (which only knows
about CONSTRUCTORS, not army units) and sat on IDLE. Not the same gap as the
idle-tree-reclaim fix elsewhere in this file -- that fix only reaches trees.

**Fix, two parts:**
1. New C++ query `CCircuitAI::GetOwnDamagedNear(pos, radius)`
   (`cpp/src/circuit/CircuitAI.cpp`/`.h`), mirroring the existing
   `GetOwnStructsNear`/`GetOwnUnitsOfDef` pattern already in this fork: our
   own live, finished, MOBILE units under 100% health within radius. Bound to
   AngelScript as `ai.GetOwnDamagedNear` (`cpp/src/circuit/script/
   InitScript.cpp`).
2. `Builder::RezzerRepairNearby` (`manager/builder/rules_rezzer.as`), wired
   into `AiMakeTask`'s floor (`manager/builder/maketask.as`) ABOVE
   `IdleFeatureReclaim` -- per apexearth's own framing, keeping an existing
   unit alive outranks salvaging a tree. Rate-limited on the existing
   `REZ_WRECK_PERIOD` global cooldown; radius reuses `WRECK_SEARCH` (2200,
   the same bot's own existing wreck-search reach) rather than a new number,
   since `assist.as`'s `ASSIST_RANGE` is not visible yet at this point in the
   include order (`assist.as` loads after `builder.as` in `main.as`).
   `aiBuilderMgr.Enqueue(TaskB::Repair(NORMAL, target))` is the exact call
   already proven safe for re-election every tick in `rules_commander.as`'s
   factory-assist rule -- the engine dedupes REPAIR tasks by target id
   (`BuilderManager.cpp:700-703`), so repeated enqueues of the same target are
   free.

**Cost:** none against expansion -- fires only in the same floor tier as
`IdleFeatureReclaim`/`Assist::Fallback`, when nothing else claimed the bot.
Scoped to `IsRezzer(unit)` only, not extended to ordinary constructors (which
already reach `DefaultMakeTask`'s own REPAIR offers for buildings and other
builders under construction).

**NOT YET LIVE.** This is a C++ change (`cpp/src/circuit/CircuitAI.{cpp,h}`,
`cpp/src/circuit/script/InitScript.cpp`) plus the AngelScript that calls the
new binding. Per the task's own instruction, no match/build/deploy was run
this session -- needs the cross-compile toolchain (`docs/06-building-the-dll.md`),
a rebuild of `SkirmishAI.dll`, `deploy_ai.py deploy apex`, and a watch/match to
confirm both that it compiles and that rez bots actually pick up the new task.

## 2026-08-14: builders thrashing mid-walk, and no reclaim-idle fallback -- FIXED (live-confirm pending)

apexearth, live-watching Altair_Crossing_V4.1: a constructor headed to mex A,
turned around toward B, stopped, changed again; and idle builders stood still
next to reclaimable trees instead of reclaiming them.

**Thrashing.** `Builder::HoldWorkInProgress` (`manager/builder/rules_hold.as`)
is the general-path stickiness for an in-progress task -- it returns the
currently held task unchanged on every re-election, matching the fix already
applied to `CommanderTask`. But it gates on `SiteBuildName(busy) != ""`, and
`SiteBuildName` (`manager/builder/sitesafety.as:245`) deliberately excludes
`Task::BuildType::RECLAIM`. So a builder mid-reclaim (wreck or, after the
change below, a tree) fell through every tick, `AiMakeTask` recomputed a fresh
`DefaultMakeTask` offer (a different build type, e.g. MEX), and
`IBuilderTask::Reevaluate` swapped the unit off the walk it was already on --
the exact re-election trap CLAUDE.md documents, just not yet covered outside
`CommanderTask`. Fixed by holding a RECLAIM task the same way, since
`AbandonUnsafeSite` already re-checks reclaim safety every tick and refuses it
explicitly when it goes hot -- a reclaim that survives that check is exactly
as "still wanted" as a mex.

**No idle-reclaim floor.** Confirmed no rule proposed reclaiming neutral map
features (trees) at all. `Builder::ScavengeWrecks`/`EnqueueWreckReclaim`
(`manager/builder/rules_scavenge.as`, `reclaim.as`) only ever call
`ai.GetBestWreckPos` with `minMetal` 15/55/400 -- floors sized to avoid
displacing real work for a 12-metal tree, which by design also exclude trees
from the truly-idle case where nothing is being displaced.
`Builder::TidyObsolete`/`ObsoleteReclaim` (`obsolete.as`) only reclaims OUR
OWN named buildings, never neutral features. Added
`Builder::IdleFeatureReclaim` (`reclaim.as`), placed in `maketask.as`'s
genuinely-idle floor (`task` already null, every productive rule above
declined) -- below `TidyObsolete`, above `RezzerPreemptReclaim`/
`CommanderIdleWork`/`Assist::Fallback`. It reuses `EnqueueWreckReclaim`
(given an optional `minMetal` param, default unchanged at `WRECK_MIN`) with
`minMetal=1`, so `GetFeaturesIn`'s existing tree/wreck sweep and the existing
`ThreatFor`/`CON_THREAT_VETO` safety check are reused rather than any new
scoring logic. Excluded for the commander (`CommanderIdleWork` already covers
it). The new reclaim task is itself now held by the `HoldWorkInProgress` fix
above, so it will not itself thrash.

Files: `manager/builder/rules_hold.as`, `manager/builder/reclaim.as`,
`manager/builder/maketask.as`. Not yet measured against a live/tournament run
per instruction (no match launched); `tools/check.py` passes with no new
errors. See `ISSUES.md` for the live-confirm entry.

## 2026-08-14: solo-path Attack() walked units into tower range to "confirm LOS" -- NOT YET LIVE-CONFIRMED

apexearth, watching, immediately after the fragility fix below went live:
"I'll have one hound standing outside range shooting at a tower, then the
next will walk into range of that tower and shoot at it and die." A
per-UNIT divergence within the same row, distinct from the squad-wide
standoff-distance bug the earlier fixes address (those all live in
`ISquadTask::Attack`, `SquadTask.cpp:576-924`, and apply uniformly per row).

Found in `CCircuitUnit::Attack(pos, enemy, isGround, isStatic, timeout)`,
`cpp/src/circuit/unit/CircuitUnit.cpp:530-575` -- the function every fighter
task (squad and solo) actually calls to execute the standoff position
computed elsewhere. It has an internal `prefer` gate:
`prefer = !isGround && !melee && enemy->IsInLOS()`. When true, only the
standoff-ring move order is issued (correct). When false, it ADDITIONALLY
queues `unit->Attack(enemy->GetUnit())` and `CmdFightTo(enemy->GetPos())` --
literally the target's own ground position, not the ring -- with the
comment "a contact held on radar only... the fight order IS the walk-in
that gains LOS." That rationale is for mobile radar-only ghosts.

For a STATIC target (a tower) this fires far more than a rare race:
`enemy->IsInLOS()` is confirmed real-time per-frame team vision
(`EnemyManager.cpp:155,169,180`, updated every tick from the engine
callback, not "ever seen"), and a row's correct standoff distance is its
own WEAPON range, which routinely exceeds its SIGHT range -- Hound is 650
range vs ~400 sight, the same asymmetry the squad-path LOS-floor fix
(`SquadTask.cpp:751-768`) exists to handle. So a Hound correctly holding
650-range standoff on a tower with nothing else giving the team LOS on it
reads `IsInLOS()==false`, and the next time THAT unit individually gets
reissued (new squad member, `isRepeatAttack` tick, retreat-and-rejoin) it
gets the fallback branch and walks to the tower's own position -- past its
own standoff ring, into weapon range, while an already-settled squadmate
(last reissued at a moment LOS happened to read true, or simply not due for
reissue) sits still at the correct distance. Same row, same target, two
different per-unit histories -- exactly the reported shape.

**Fix**: for `isStatic` targets, position is known with certainty and never
moves, so there is nothing to "confirm" by walking closer -- skip the LOS
requirement: `prefer = ... && (isStatic || enemy->IsInLOS())`.
`cpp/src/circuit/unit/CircuitUnit.cpp:551-552`. This makes ring-standoff-only
orders unconditional for towers/static defence, for every fighter task that
routes through this function (squad AND the solo `IFighterTask::Attack` path
used by `ScoutTask`).

Rebuilt via the docker toolchain (`ninja -C /build/out BARb`, 1 object
recompiled). NOT yet deployed or watched -- a live game was running when
this was found; deploy and watch before trusting it fixed. See `ISSUES.md`.

## 2026-08-14: SAME REPORT AFTER the LOS-static fix above shipped -- second, distinct mechanism, standoff margin could land inside a near-parity tower's range

apexearth, watching Altair_Crossing_V4.1 with tonight's `isStatic ||
enemy->IsInLOS()` fix (above) already built and deployed *before* this game
started -- confirmed by DLL timestamp (build 14:42, match start 14:48) and
`sync_cpp.py status` showing `cpp/`/`vendor` in agreement: "I see rocket bots
walk into turrets and die too... they're similar in logic to hounds I
think... they out range these things but walk into their death... btw yeah
hounds still make this mistake." So the LOS-reissue bug was NOT the (only)
cause -- do not re-diagnose that mechanism, it is fixed and still live.

Second mechanism, in `ISquadTask::Attack`, `SquadTask.cpp:744-746` (before
this fix): when a row is NOT `outranged` (its own weapon range >= the
target's), `standoff` is set to `kv.first` -- the row's OWN range, with no
reference to the target's range at all -- and then unconditionally shrunk by
`rangeMod` (`STANDOFF_RANGE_MOD = 0.90`). That 10% shrink has no floor
against the target's actual range, so any target whose range sits within
90-100% of the row's own range reads as "we outrange it" (true, technically)
while the shrunk stand-off distance lands INSIDE its reach anyway. Confirmed
with `tools/unitdef.py`: Hound (`armfido`) has 650 weapon range against
`corhlt` (Warden, Cortex's Area Control Laser Tower) at 620 -- 650*0.9=585,
short of 620 by 35 elmos. The "dive in on purpose" exemptions
(`isArty`/`powerDominant`/`glassCannon`, same branch) don't apply here: none
of them read true for a tower against a T1/T2 skirmisher bot, so this is the
"genuinely outranges" case losing its own margin, not an intentional close.
`armrock`/corresponding Rocketeer-class rocket bots hit the same shape against
any tower in the same 90-100%-of-their-range band, matching "rocket bots... do
the same thing" in the same report.

**Fix**: added `weOutrange` (`!outranged` branch AND raw range check AND none
of the dive exemptions) and floor the final computed `range` at
`edef->GetMaxRange() * OUTRANGED_SAFETY_MARGIN` (1.1x) when `weOutrange` is
true, so the 10% margin can never eat into a genuine but narrow range
advantage. `cpp/src/circuit/task/fighter/SquadTask.cpp:744-763`. Intentional
dives (arty/glass-cannon/power-dominant targets) are unaffected -- the floor
only applies in the branch that was never meant to close distance at all.

Rebuilt clean via the docker toolchain (1 object recompiled,
`SquadTask.cpp.obj`), `sync_cpp.py status` confirms `cpp/`/`vendor` match.
**NOT deployed, no match run** -- per instruction, a watch game was in
progress. Deploy and watch before trusting this closes the symptom; if Hounds
still dive into towers after this is live, the remaining candidate is the
per-row "scout" exception at `SquadTask.cpp:766-769` (floors only the first
unit of the first row, should never reduce distance, but re-check under a
live game) or a task-type routing question (does this Hound/Rocketeer squad
actually go through `ISquadTask::Attack` at all, or some other task class --

## 2026-08-14: fragile-unit standoff/angle scaling -- broader ask than the Hound fix above

apexearth, watching, AFTER the standoff/LOS-floor/ring-safety fixes above:
"Hounds (low los high range unit) still walk much too close to enemies. They
aren't tough - they really need to be more careful with themselves...
certain lower hp units have to be way more careful than high hp units." A
distinct, broader ask than the earlier three-part fix: caution should scale
with the unit's OWN survivability, not be one flat number applied to a
glass-cannon Hound and a tanky Mammoth alike.

**Checked for a separate kiting/skirmisher code path first** (per the task
brief) -- `cpp/src/circuit/task/fighter/` has no such thing; `ArtilleryTask`,
`AntiHeavyTask` etc. are role dispatchers, not a different standoff
mechanism, and every fighter task funnels through the same
`ISquadTask::Attack` (squads) / `IFighterTask::Attack` (lone units) standoff
code the earlier fix already touched. So the earlier fix DOES reach the
Hound case mechanically; what it lacked is any per-unit scaling at all --
`STANDOFF_RANGE_MOD` (0.90) and the ring-safety 10% threat-gap threshold are
both flat constants applied identically regardless of `CCircuitDef::
GetHealth()`. `GetRetreat()` (`FighterTask.cpp:171-177`, `CircuitDef.h:368`)
is a per-unit-def value already, but it comes from a hand-set JSON number per
unit (`behaviour.json`'s `"retreat"` field -- armfido is `0.5`, same
ballpark as most other T2 assault bots) rather than anything derived from
HP/armor, so two units with very different toughness can carry the same
number by coincidence of whoever tuned the JSON.

**Fix, `ISquadTask::Attack` (`SquadTask.cpp`), squad path only** (the single-
unit `IFighterTask::Attack` path has no equivalent standoff-scaling block to
extend, same scope note as the pre-range-veto fix earlier tonight). Computes
one `fragility` ratio per row: `avgSquadHealth / rowDef->GetHealth()`,
clamped to `[1, FRAGILE_CAP]` (`FighterTask.h`, default 2.0) -- baseline is
THIS squad's own average `CCircuitDef::GetHealth()` across every row actually
fighting together right now, not a global constant, so a Hound reads as
fragile only when it is actually the squishy one in the mix it is deployed
with, and the same code covers any low-HP def on any faction with no
per-unit branch. Applied two places already using flat constants:
1. Standoff distance: `range *= 1 + (fragility-1) * FRAGILE_STANDOFF_SCALE`
   (default 0.25) -- a row at half the squad's average HP stands ~25%
   further out than the flat 90% margin already gives it.
2. Ring-side safety selection (`SquadTask.cpp:~816`, the just-landed
   "choose safer angles" threat comparison): threshold divided by
   `fragility`, so a fragile row needs a smaller threat gap between the two
   candidate standoff points to prefer the safer one.
Both new constants are tunables (`apex_fragile_standoff_scale`,
`apex_fragile_cap`) with the values above as the measured-nothing-yet
default, per CLAUDE.md's "make it a tunable with the measured default" --
not a hard cap, since `fragility` itself is derived per-squad every call, not
fixed.

**Build.** `cpp/` -> `vendor/engine` via `sync_cpp.py apply`, rebuilt via the
docker toolchain (`ninja -C /build/out BARb`, 35 objects, both touched files
recompiled, linked clean, no new warnings from this change), `sync_cpp.py
status` confirms `cpp/` and `vendor` match. **Not deployed and no match run**
per instruction -- a watch game may be running.

**VERDICT: mechanism reaches the reported case (confirmed by code reading,
not benchmark) and is a real generalization of the flat-constant gap, not a
Hound special case.** COST: none to the economy -- this only changes standing
distance/angle choice for units already in the same task, no new work
enqueued. CONFIDENCE: moderate. The formula and clamp direction (only ever
ADD caution, never remove it from an above-average unit) are argued from the
code, not measured -- no self-play run was done this session (explicitly out
of scope: no deploy/match). What would confirm it: a self-play 1v1 with
Armada in the mix (Hound actually present) showing the fragile row's
standoff distance in a squad log, or a before/after K/D on a mixed-composition
army. What would falsify it: if `avgSquadHealth` in practice is usually
computed over a near-uniform-tier squad (rows rarely differ much in HP within
one task), in which case `fragility` stays ~1 and this never fires -- not
checked; squads are grouped by weapon-range key (`rangeUnits`), not by unit
type, so a squad CAN contain multiple distinct defs, but how often it
actually does in this AI's real compositions is unverified.

that was not in any danger, then walked away instead of claiming it.
Mechanism: `EconomyManager.cpp:1000`'s `FindOpenMexSpot` -- the only mex
search a script can run -- excludes ally-zone spots on purpose
(`!terrainMgr->IsZoneAlly(p)`; it exists for frontier reroutes). So
`brain.as`'s `MexWant` never proposes a home mex at all, and cannot win it in
`Brain::Decide`'s ranking. The engine's own native mex-task creation
(`DefaultMakeTask`) does still cover home spots, but only on its own scan
cadence, not synchronously with a builder's next election
(`Builder::MakeTaskInner`, `maketask.as:102`). In that gap, an idle builder's
election ran `Brain::Decide` with no mex want in the pool at all, so an
optional want (gantry, nano, ...) -- which doesn't depend on `FindOpenMexSpot`
-- won instead and sent it walking.

Fixed by taking the engine's own mex offer (once it arrives, safe) ahead of
every optional want rather than letting it compete inside `Brain::Decide`:
`Builder::MexOffer` (`manager/builder/rules_offer.as`), called right after
`DefaultMakeTask` in `maketask.as:120`, before `OpeningEnergy`/
`Brain::Decide`. Tunable `apex_take_mex_offer` (default on). This narrows the
idle window but does not close it -- the tick before the engine's scan
reaches the spot, an optional want can still fire first; the underlying gap is
that no script-side query for an ally-zone open mex spot exists (`FindOpenMexSpot`
is the only one, and it deliberately excludes them). Closing that fully needs
a new/adjusted C++ binding, not landed here. Not yet confirmed against a fresh
watched game -- see `ISSUES.md`.

## 2026-08-14: first high-quality static defence landed in a map corner instead of at home

apexearth, watching a 1v1: the AI's first significant defence tower appeared
off in a corner of the map rather than in/near its own base. Layer 2
(AngelScript), `manager/military/territory.as:92` `BorderPos()` -- the
placement function behind the big gun (`UpdateFrontGun`,
`manager/military/defenceline.as:22`), the T3 dome/pulsar, and the line

Mechanism: `BorderPos` ranked every metal cluster we hold (`gSitePos`, one
entry per taken cluster) purely by `score = (cover + 1) * distanceToEnemy`,
lowest wins -- with no term for distance from home at all, and no check that
the site is on any actually-contested ground. Early game, with only the home
base and one forward expansion mex claimed, the expansion mex is very often
literally closer to `aiEnemyMgr.GetEnemyPos()` (the enemy centroid) than the

of whether anyone has ever fought near it. The big gun -- the first
high-value tower the AI ever builds -- went there.

tracks which bearings around our territory are actually crossed by contested
influence (`OnBorder`). `BorderPos` never consulted it. Fixed by gating
eligibility on `OnBorder(site)` once a front exists (`haveFront =
gFrontValid && gRayR.length() > 0`), so an unpressured outpost we merely own
no longer outranks the base by being nearer the enemy's average position; and
by falling back explicitly to `Builder::gHomePos` for rank 0 when no site is
on an established line yet -- the honest answer for "where should our first
defence go" before there is a real front to anchor it to. Not a distance cap:
a legitimate pushed front position still wins once contact has actually put
it on `OnBorder`, at any distance.

Not yet confirmed against a fresh watched game (one may be running) -- see

## 2026-08-14: squad-relative "screen the hurt unit" retreat, measured on a 1v1 mirror

apexearth, watching several games: "our army doesn't fight as unified as the
other army... we give up on successful attacks too quickly." Prior session
diagnosed the mechanism (`military/posture.as:170-178`): outside a declared
`TEAM PUSH`, `ai.SetCommitted(false)` is the normal state, so `CCircuitAI::
IsCommitted` lets each unit peel off individually at its own `GetRetreat()`
threshold -- a squad dissolves one unit at a time. Forcing full commitment
outside a push was tried and reverted (army K/D 0.38 vs stock 1.73). His
refinement: don't force them to fight to the death OR send them all the way
home -- "best would be if the hurt guys just move towards the back of the
pack," screened by healthier squadmates, still in the fight.

**Mechanism.** `IFighterTask::OnUnitDamaged` (`FighterTask.cpp:144-207`)
already has a middle state that was going unused for exactly this: a unit
at/below `GetRetreat()` health is inserted into the `cowards` set (not sent
to `CRetreatTask`) whenever it is still safe -- target in LOS, in range,
threat tolerable (`FighterTask.cpp:191-206`). It keeps fighting at its normal
squad slot and only retreats once it goes idle. The gap was purely
positional: `ISquadTask::Attack`'s per-unit standoff `r` (`SquadTask.cpp:805`,
the radius each unit stands from the target on its row's arc) made no
distinction for a `coward`. Changed `r` to a `float` and multiplied it by
`apex_coward_rear_mod` (default `COWARD_REAR_MOD = 1.35`, `SquadTask.h`) for
any unit in `cowards` -- it stands 35% further out on the SAME ring, which
puts healthier squadmates on the same bearing between it and the target,
instead of leaving the formation. This is not the reverted "never retreat"
change: that forced every unit, healthy or not, to fight in place until
death; this only repositions units `OnUnitDamaged` already judged safe enough
not to need a full retreat. `cpp/src/circuit/task/fighter/SquadTask.cpp:805-
816`, `SquadTask.h` (new `COWARD_REAR_MOD` define). Rebuilt via the docker
toolchain (`ninja -C /build/out BARb`), compiled clean, redeployed
(`deploy_ai.py deploy apex`, confirmed "SkirmishAI.dll (local build)").

as an identical confound across both runs -- not a code effect), 1v1 Cortex

## 2026-08-14: the "hold instead of stepping into a hotter spot" threat-veto had no in-range check, so an approaching unit could get stuck holding position with a target set

apexearth: "sometimes our units will set target on an enemy unit but they
aren't within range. They should be setting target but still have actual
move logic happening which maneuvers them within the range of the enemy."

**Mechanism.** `ISquadTask::Attack` (`SquadTask.cpp:816-844`) computes each
unit's standoff point `newPos` on a ring at its own weapon range from the
target, then (added 2026-08-13 for a different complaint, "retreat logic
takes us into new threats") compares threat at `newPos` against threat at
the unit's current position `curPos`; if `newPos` reads hotter, it replaces
`newPos` with `curPos` -- hold instead of step. That veto had no distance
check at all. `newPos` sits, by construction, at the unit's own weapon range
of the target -- inside or adjacent to the target's own threat radius for
any direct-fire matchup -- so for a unit that has NOT yet reached firing
range, almost every candidate step compares hotter than staying put, and the
veto holds it at `curPos` indefinitely. `CmdSetTarget` still goes out on the
same call (`CCircuitUnit::Attack`, `CircuitUnit.cpp:568-569`), so the unit
visibly has a target locked while never approaching it -- exactly the report.
The comment introducing the veto was explicit that it meant "enemies we're
actively fighting," i.e. a unit already in range choosing not to step into a
second enemy's range; it was never meant to gate the initial approach, but
nothing in the code enforced that scope.

**Fix.** Gated the veto on the unit already being within its own standoff
range of the target (`curPos.SqDistance2D(tPos) <= SQUARE(r * 1.05f)`, `r`
being the same per-unit ring radius already computed a few lines above for
`newPos`). A unit still closing distance is no longer eligible to be held in
place by this check at all -- it always gets the move-toward-range order;
only a unit already trading fire can choose to hold rather than step into a
worse spot. `cpp/src/circuit/task/fighter/SquadTask.cpp:833-850`. Left
`FighterTask.cpp`'s equivalent single-unit `Attack` path (non-squad fighters)
untouched -- it has no such threat-veto block, so it was not part of this
bug. Rebuilt via the docker toolchain (`ninja -C /build/out BARb`), compiled
clean, pulled into `cpp/` via `sync_cpp.py pull`, cumulative patch
regenerated.

## 2026-08-14: the recurring crash — found and fixed (IRefCounter use-after-free in DequeueTask)

Layer 3 (C++), `module/TaskModule.cpp`. Full writeup in `ISSUES.md`
("RESOLVED" entry) -- summary here for the changelog.

`ITaskModule::DequeueTask` called `task->Stop(done)` immediately after
`TaskRemoved(task, done)`, which fires the AngelScript `AiTaskRemoved`
callback with a bare native pointer and no reference held across the call.
`IUnitTask` is `asOBJ_REF` with intrusive refcounting (`RefCounter.cpp`), so
if that callback happened to drop the last script-side reference (e.g. the
last element removed from `Requests::gLive`), AngelScript legitimately
deleted the object right there, and `task->Stop(done)` one line later was a
use-after-free on the same function's own raw pointer. This is the same bug
class as `changes/2026-08-09.md`'s "C++ deleted tasks the script held," just
the other direction -- script deleting an object native code still needed,
instead of native deleting one script still held.

Found via Windows Application Verifier (`appverif -enable Heaps -for
spring-headless.exe`; no rebuild needed, disabled again after with `-disable
* -for spring-headless.exe`) plus the existing `addr2line`-against-unstripped-
build pipeline from earlier tonight -- AppVerifier didn't catch this
specific bug directly (it's not raw OS heap corruption; AngelScript uses its
own internal pool), but running under it still produced a crash whose stack
pointed straight at the real line. This explains why the crash surfaced at
four different-looking call sites across the session (`CIdleTask::Update`,
`MakeBuilderTask`, `MakeCommDangerTask`, `CBuilderManager::UnitIdle`) and
evaded two sessions of manual auditing -- same root cause, different
downstream victim each time depending on what happened to dereference the
dangling pointer first.

Fix: bracket the callback with the object's own `AddRef()`/`Release()`, the
same guarantee every other handle-holder already gets from AngelScript.
Rebuilt via docker, verified clean AS compile and unregressed opening timing
on redeploy. Not run long enough yet to positively confirm the original
crash can't still happen some fifth way, but the mechanism came from the
crash's own stack, not inference, and the fix is the standard pattern for
exactly this shape of bug.

**Deployed together with three other staged fixes**, all from tonight's

## 2026-08-14: standoff range tightened to 90%, the LOS-scout mechanism could pull a unit well inside that standoff, and ring-side selection now weighs threat

apexearth, watching live, follow-up to the pre-range threat-veto fix above:
"When we are doing this maneuvering while using 'set target' we should aim
to be at around 90% of our maximum attack range. We should not move any
closer, and we should try to choose safer angles. Right now I see our hound

Attack`, `cpp/src/circuit/task/fighter/SquadTask.cpp`.

**1. Standoff was 95% of own range, not 90%.** `STANDOFF_RANGE_MOD`
(`FighterTask.h:19`, runtime `apex_range_mod`) was `0.95f` -- close enough to
the weapon's edge that the enemy's own return fire reaches on a same-range
matchup or the slightest closing move. Changed default to `0.90f`, matching
the number he gave directly.

**2. The actual "running too deep" mechanism: the LOS-standoff scout had no
floor.** `SquadTask.cpp:722-727` (now :722-740) sends the first unit of the
first row to `min(kv.first, rowDef->GetLosRadius()) * rangeMod` instead of
the normal standoff, whenever the target is static or not currently in our
LOS -- so that unit can get a visual lock rather than fight blind. Read
armfido (Hound) from the pinned tree per the 2026-08-09 EyesForTheGuns note:
**650 weapon range, 400 sight.** For a Hound-shaped unit that condition
computes `min(650, 400) * 0.9 = 360` -- 55% of its own range, deep inside
where a 650-range enemy gun reaches it right back. The condition is not
Hound-specific: `isStatic` alone triggers it, so it also fires on every
static-defence target regardless of the attacker's own sight, which is why
the isolated self-play test below (Cortex, no Hound in the roster at all)
still measured a real effect from this line. Floored `range0` at `range`
(`std::max(range, ...)`): a row whose sight already reaches its own standoff
gets the same value as before (no-op, verified: `min(kv.first,losRadius) *
rangeMod` already equals `range` whenever `losRadius >= kv.first`), and a
row that does not is no longer sent closer than the standoff to get there.
The mobile-radar escort added 2026-08-09 (`EyesForTheGuns`) is the intended
fix for genuinely blind guns now; this scout mechanism should not also be
sending the gun itself into danger to solve the same problem twice.

**3. Ring-side selection had no safety preference.** `SquadTask.cpp:768-777`
(now :768-794) computes two candidate ring ends (`newPos1`/`newPos2`,
mirror images of the same standoff arc) and picked whichever was less travel
for the row's lead unit -- pure geometry, no read of what was actually on
either side. Added a threat comparison using the same `CThreatMap::
GetThreatAt` the standoff veto already calls, sampled once per row on the
two candidate ends: the meaningfully-safer side (>10% threat difference)
wins outright, and distance is kept only as the tiebreak when neither side
reads as more dangerous, so the formation does not zigzag between two
near-identical tiles every update.
